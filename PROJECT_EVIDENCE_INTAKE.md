# Project Evidence Intake

Use this file to collect the facts needed before publishing a client delivery case study. A reference architecture explains a possible design. A case study must show what Vakratron actually delivered, the evidence for it, and the result achieved in that engagement.

Do not publish a client name, logo, exact architecture, invoice, purchase order, or performance result without the client's written approval. If the client cannot be named, publish the sector, scale band, project period, and an approved anonymised description instead.

## Evidence required for every project

1. **Public title:** A plain description of the delivered result. Example: `Private AI platform for a regulated financial-services organisation`.
2. **Client disclosure:** Named client, approved anonymous description, or approval pending. Record the approver and the date.
3. **Problem statement:** The concrete constraint that started the work. Include the business impact, the existing platform, and the risk of keeping it unchanged.
4. **Vakratron scope:** State what Vakratron designed, supplied, configured, migrated, integrated, tested, or operated. Do not claim work delivered by another party.
5. **Architecture:** A redacted diagram that shows the meaningful components and data flows. Include only approved technology names and environment details.
6. **BOM or BOQ evidence:** Provide vendor, model or SKU, quantity, and the role of each component. Remove commercial rates, serial numbers, credentials, and customer addresses before publication. If hardware was not supplied, publish the software, cloud, and service components instead.
7. **Implementation method:** Explain the discovery, build, migration, validation, security review, handover, and rollback controls actually used.
8. **Measured outcomes:** Baseline, post-implementation value, measurement method, measurement period, and owner. Label a target as a target; never present it as an achieved outcome.
9. **Supporting artefacts:** Approved redacted documents such as a sign-off, architecture extract, test report, acceptance certificate, runbook excerpt, or client testimonial.
10. **Review owner:** The person who confirms that the public page is accurate, approved, and current.

## Publishing standard

Each public case-study page should use this order:

1. Client context and disclosure status.
2. Problem and baseline.
3. Vakratron scope.
4. Architecture diagram and component roles.
5. Redacted BOM or stack.
6. Implementation and validation method.
7. Measured outcome with period and source.
8. Approved evidence and reviewer.

Avoid claims such as "zero downtime", "guaranteed", "best-in-class", "production-grade", or a percentage improvement unless an approved source in the project file supports the claim.
